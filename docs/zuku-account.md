# ZUKU 계정과 게임 배포

`zuku`와 `zukujs`는 같은 로그인 정보와 실행 상태를 사용합니다.

```sh
zuku login zuku
zuku account --quota
zuku deploy ./my-game --yolo
zuku account logout
```

로그인은 공식 ZUKU 브라우저 페이지에서 계정을 확인하고 연결을 승인하는 방식입니다. CLI는 비밀번호나 복사한 토큰을 요구하지 않습니다. `--no-browser`를 사용하면 표시된 공식 페이지를 직접 열 수 있습니다. `--yolo`는 검증된 게임을 즉시 공개 게시할 의사 표시이며 추가 단계별 승인 질문은 없습니다.

공개 클라이언트 ID는 `zuku-cli`이며 기본 권한은 `games:upload games:create games:publish`입니다. 일반 웹 로그인, 개발자 키, 환경 변수의 다른 인증 정보로 자동 배포 권한을 대신할 수 없습니다. `login zuku --generate`는 기존 AIST 토큰 할당량을 사용하는 `games:generate` 권한도 **명시적으로** 요청합니다. 이 추가 권한은 서버의 검토된 native 게임 API와 승인 페이지가 제공되어야 사용할 수 있습니다. 기존 세 권한 연결은 게임 업로드와 배포에 계속 사용할 수 있습니다. 모델 가용성이나 실제 생성 성공은 별도로 확인합니다.

서버는 계정당 최근 6시간 동안 성공한 공개 배포를 최대 3회 허용합니다. 결과가 아직 확정되지 않은 예약도 한도를 차지합니다. `account --quota`는 성공 수 `used`, 미확정 수 `pending`, 남은 수 `remaining`, 회복 시점 `reset_at`과 대기 시간 `retry_after`를 보여 줍니다. 다른 장치나 동시 실행에도 서버의 같은 한도가 적용됩니다. 초안과 업로드는 성공 배포 횟수를 소비하지 않습니다.

게시 전에 `.zukujs/receipts` 또는 지정한 `--receipt-dir`에 계정·작업 키·패키지 전체 SHA-256·크기를 묶은 복구 기록을 저장합니다. 초안 생성과 게시가 같은 `Idempotency-Key`를 사용합니다. 같은 소스의 확인된 완료 결과를 조회하는 재실행은 다시 게시하거나 한도를 추가로 소비하지 않습니다.

응답이 끊기면 같은 작업 키의 서버 상태를 조회합니다. 현재 소스와 크기가 일치하고 `source_verified:true`인 완료 상태만 성공으로 인정합니다. `publishing` 또는 `uncertain`은 자동 재게시하지 않습니다. 소스가 확인된 초안이어도 예약이 미확정이면 운영 측의 명확한 상태 정리가 필요합니다. 다른 키를 만들거나 로컬 기록을 지워 이 상태를 우회하지 마세요. 저장된 배포는 다음처럼 확인할 수 있습니다.

```sh
zuku deploy --content cnt_EXAMPLE --yolo --receipt-dir .zukujs/receipts
```

이 명령에는 같은 설치에서 보존한 복구 기록과 원래 계정 연결이 필요합니다. 에이전트의 `--resume`도 같은 기록으로 조회부터 수행합니다. 전체 게임 원문이나 인증 토큰은 배포 영수증에 저장하지 않습니다.

Unix 계정 저장소는 사용자 소유 디렉터리와 권한 0600 파일을 사용하고 링크를 거부합니다. Windows는 현재 사용자 DPAPI 암호화와 사용자 전용 ACL 검증을 사용하며 평문 저장으로 대체하지 않습니다. 로그아웃은 토큰 없는 기록을 남겨 늦게 도착한 로그인이나 갱신이 연결을 되살리지 못하게 합니다. 계정이 변경되면 기존 제작의 배포를 중단합니다. 갱신 응답이 유실되면 이전 갱신 토큰을 재전송하지 않고 재로그인을 요구합니다.

이전 시험용 서버의 계정 기록은 자동으로 새 인증으로 변환하지 않습니다. `ZUKU_ACCOUNT_MIGRATION_REQUIRED`가 나오면 `zuku login zuku`로 공식 연결을 다시 승인하세요. 기존 게임 프로젝트와 CLI 설정 경로는 유지됩니다.
